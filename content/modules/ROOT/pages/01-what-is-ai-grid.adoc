= What is AI Grid

This page defines {aigrid}: the problem it solves, who operates it, what a provider and a tenant can each do, and where the boundaries of the model are.

== Definition

{aigrid} is a way for a service provider to offer {maas} ({maas-short}) across several {ocp-short} clusters from one place, behind a single gateway, and to onboard customers as tenants using subscriptions.

Three properties define it:

Multi-cluster::
Model endpoints span several clusters. The grid presents them as one catalog, and routes each request to a site that can serve it.

Single gateway::
Clients get one entry point and one credential. They do not track per-cluster endpoints, per-cluster hostnames or per-cluster keys.

Subscription based tenancy::
A tenant is onboarded with a subscription that defines which models it can reach and at which quota. Access, usage and visibility are separated by that subscription, not by giving every tenant its own deployment.

The short way to say it: *several clusters behave like one governed serving environment.*

== The Problem It Solves

Running models on more than one cluster without a grid means repeating everything per cluster:

* One gateway per cluster, so applications have to know which cluster holds which model
* Deployment, policy and observability work repeated cluster by cluster
* No shared usage record, so nobody can connect GPU consumption to a tenant, an application or a model
* Tenant onboarding built by hand for each customer

The alternatives are both bad. Either you collapse everything into one large cluster, which wastes a distributed footprint and ignores where the data has to live, or you run a bespoke integration project per customer.

Providers that own data centers, power and regulatory standing in their market want to serve AI from that footprint. What they need is a way to operate inference capacity spread across sites as a single service.

== Who It Is For

Telecommunications and cloud service providers, and large enterprises acting as internal providers, that run GPU capacity on more than one {ocp-short} cluster and want to expose models to many customers or business units without giving them access to the infrastructure.

== Personas

Three roles operate a grid. The separation between them is the core of the tenancy model.

[cols="1,2,3", options="header"]
|===
| Persona | Example | What they do

| *Provider admin* (grid admin)
| The platform team of a service provider
| Creates the multi-cluster {maas-short}, publishes models onto it, onboards tenant administrators, issues subscriptions, and sees usage across all tenants at the gateway.

| *Tenant admin* (organization admin)
| The AI platform lead of a customer
| Accepts a subscription and manages which of their own users can call the model endpoints, within the limits of that subscription. Does not deploy models and does not see other tenants.

| *Tenant user* (organization user)
| A developer at that customer
| Calls model endpoints through the gateway with their own credentials, manages their own API keys, and sees their own consumption.
|===

The provider owns infrastructure and catalog. The tenant owns who inside their organization gets access. The user owns their keys and their requests. No tenant touches the underlying clusters.

== How It Works End to End

[cols="1,4", options="header"]
|===
| Step | What happens

| *1. Deploy*
| The provider admin creates the multi-cluster {maas-short}: one gateway, the clusters it spans, no models yet. The platform installs and configures the serving, gateway and grid components on each selected cluster.

| *2. Publish*
| The provider admin deploys models onto it. Each model becomes an endpoint behind the single gateway, served from the cluster or clusters the admin chose.

| *3. Onboard*
| The provider admin registers a tenant, connects it to identity, and issues a subscription that defines which models that tenant can reach and at which quota.

| *4. Grant*
| The tenant admin gives their own users access within that subscription, by managing group membership in their own identity provider. Users then call the endpoints with standard OpenAI compatible APIs.

| *5. Record*
| Every call through the gateway is recorded against the tenant's subscription: model, tokens, and the cluster that served it. The provider sees usage across all tenants; the tenant sees their own consumption against the subscription limits.
|===

NOTE: Clusters are expected to exist already and to be registered for multi-cluster management. "The platform provisions the infrastructure" means it installs and configures the grid components, gateway wiring and serving runtimes on each selected cluster. Creating the clusters themselves is a separate concern.

== What Stays Inside the Provider

Models run on the provider's clusters, and requests are served from them. The gateway, the clusters and the data stay where the provider deploys them. That is what makes the model usable for in-country and regulated-industry requirements: the provider governs and meters centrally, while serving endpoints close to the customer.

Credentials follow the same principle. A credential that a remote site needs to reach its own backend stays at that site and is never sent to the edge. See xref:04-request-flow.adoc#_credential_flow[Credential Flow].

== The Tenancy Model

{aigrid} provides *subscription-based tenancy*. Several customers can share one multi-cluster {maas-short} while access and usage are separated through identity, subscriptions, gateway policy, quotas and tenant-scoped visibility.

It is worth being precise about what that does and does not mean:

[cols="1,3", options="header"]
|===
| Model | Meaning

| *Soft tenancy*
| Logical controls separate tenants that share service and infrastructure components. Identity, subscription binding, gateway policy, quota enforcement and scoped dashboards are the boundary.

| *Hard tenancy*
| Dedicated or strongly segregated boundaries across gateway, control plane, network, clusters, compute and GPU, storage, keys and observability, potentially down to separate physical infrastructure.
|===

{aigrid} implements the soft model. Each tenant does *not* get dedicated infrastructure. If your isolation requirements go further than identity and policy, that is an infrastructure design question on top of the grid, not something the grid tenancy model provides by itself.

== What AI Grid Is Not

Being explicit here avoids most architecture discussions going in circles:

* *Not a global traffic manager.* A stable public name, edge health checking and public traffic steering belong to DNS, Anycast or a global traffic management service. The grid starts after a request reaches an edge gateway.
* *Not a billing system.* Usage is recorded per tenant at the gateway and can be exported. Rating that usage against price plans and producing invoices happens in your billing system.
* *Not a request-path control plane.* The control plane is not called during a request. See xref:02-architecture.adoc[Architecture Overview].
* *Not a cluster lifecycle tool.* It consumes clusters that already exist and are registered for multi-cluster management.
* *Not a tenant self-service deployment surface.* Tenant admins manage access for their users; publishing models is the provider's job.

== Upstream and Downstream Naming

{aigrid} is the downstream name. The upstream work is the Praxis project family, a CNCF Sandbox project under Apache 2.0. Component names differ, and both sets appear in logs, custom resources and documentation, so the mapping matters.

[cols="1,1,2", options="header"]
|===
| Upstream | Downstream | Role

| Praxis Grid, also called {agn} ({agn-short})
| {aigrid} control plane
| Prepares routing state for the gateways

| Praxis AI
| {gateway} (data plane)
| AI-aware gateway that routes the request

| Praxis ExtProc
| {gateway} external processor
| Envoy `ExternalProcessor` service, for deployments that keep Envoy in front

| Praxis Core
| Proxy and filter runtime
| Listeners, filter pipelines, load balancing, TLS, request context

| Pingora
| Proxy engine
| TCP and TLS, HTTP codecs, connection pooling, upstream I/O
|===

In this guide, {agn-short} always means the control plane and {gateway} always means the data plane.

== Prerequisites for a Grid

At a high level, a grid needs:

* {rhoai} on three or more {ocp-short} clusters with GPU nodes
* Those clusters onboarded into multi-cluster management ({acm-short})
* An identity provider for tenant users

The detailed, versioned prerequisite list belongs to the installation phase, which this guide does not cover yet.
